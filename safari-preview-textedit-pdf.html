PDFs from Safari, Preview and TextEdit: are they accessible?

Tested in October 2026 on macOS 27.

macOS makes it easy to create a PDF from almost anything. But a PDF that looks right is not necessarily readable by a screen reader. Here is what the built-in tools produce.

How we tested

We used a fictitious sample document with headings, a list, a table with a header row, two images (one with alternative text, one without) and a link, and inspected the resulting PDFs with PDF Accessibility Checker and by reading their structure directly.

Method note. TextEdit was tested through its own Export as PDF command. Safari and Preview could not be scripted on macOS 27, so their results come from the engines they are built on rather than from the apps’ menus: for Safari, the WebKit print operation of a WKWebView (the same engine that Safari uses to print to PDF); for Preview, Apple’s PDFKit framework, including for the scan-to-PDF case. We expect the apps to give the same results, but a manual export from the apps should confirm them.

TextEdit: Export as PDF

TextEdit’s File > Export as PDF produced an untagged PDF. There is no structure at all: no headings, no list, no table, nothing that tells a screen reader what the content is. The text can be extracted, but only as a flat stream.

Safari: print to PDF

The WebKit engine, printing our sample page to PDF, also produced an untagged PDF. Even when the web page itself is well structured – with real headings, lists and alt attributes on images – none of that structure reaches the PDF. In addition:

  • links were present as clickable areas but had no description, so a screen reader cannot announce where they lead;
  • the Tabs setting, which tells assistive technology to move through links and fields in structure order, was missing.

If you want to share a web page in an accessible way, sharing the page itself (the URL) is usually better than a PDF of it.

Preview: re-saving a tagged PDF

Good news here: re-saving an already tagged PDF with PDFKit kept the tags intact. If you open an accessible PDF to add a note, rotate or reorder pages, you should not destroy its structure. But PDFKit does not improve anything either: it cannot add tags, set the document language or write the title into the XMP metadata. A PDF that was not accessible before re-saving is not accessible after.

Scans turned into PDF

A scanned page saved as PDF through PDFKit is just an image: there is no text in it. A screen reader finds nothing to read, and you cannot search or copy the content. To make it accessible, the text must first be recognized with OCR (optical character recognition), and then the document must be tagged. Better still, find the original digital document and export it properly.

What to use instead

  • For text documents, use a word processor with an accessible PDF export. In our tests, Word for Mac’s accessible export worked well, apart from the declared language.
  • Pages produces tags, but with serious problems: see why the PDF from Pages is not accessible.
  • For designed documents, use Adobe InDesign with tagged PDF export.
  • Use Preview to view, annotate and reorganize PDFs, knowing it keeps but does not create accessibility.

How PDF Accessibility Checker helps
