Why the PDF from Pages is not accessible

Tested in October 2026 on macOS 27.

Pages has an Accessibility option in its PDF export, and with it turned on the file does contain tags. Yet accessibility validators report the whole document as untagged. Here is what we found, why it matters and what you can do.

How we tested

We created a fictitious sample document with headings, a bulleted list, a table with a header row, two images (one with a description, one without) and a link. We exported it from Pages with File > Export To > PDF, trying each value of the Accessibility setting, and inspected the resulting files with PDF Accessibility Checker, with veraPDF and by reading the PDF structure directly. We tested both a document created from a native Pages template and a document opened from a Word .docx file. The results describe this sample on this macOS version; other documents or later versions of Pages may behave differently.

What Pages produces

With Accessibility set to “On”, Pages writes a tagged PDF: the file contains a structure tree, the list of tags that should tell a screen reader what each piece of content is. So far, so good. The problems are in the details.

1. The tags are not linked to the content

In a tagged PDF, every tag must point to the text and images it describes, and the page content must point back to its tag. The second link goes through a table called the ParentTree. In our files from Pages the structure tree had no ParentTree. Without it, the content on the page is not connected to the tags, and validators report all content as untagged: veraPDF flags this under rule 7.1-3 of PDF/UA-1. Assistive technology that relies on this link may ignore the tags altogether.

2. Without native styles, everything becomes a paragraph

When the document came from a .docx file, or simply did not use Pages’ own paragraph styles, the headings, the list, the table and the images were all tagged as P, a plain paragraph. A screen reader user would hear no headings to navigate by, no list, no table structure, and no indication of the images.

3. Native templates: a generic heading next to H1

With a document built on a native Pages template the structure was better: real headings, list and table tags. But the main title was tagged as a generic H heading, alongside H1 headings. Mixing the generic H with numbered headings is not allowed by PDF/UA (veraPDF rule 7.4.4-2).

4. No language, no title

None of the files declared a document language, and none had a title in the XMP metadata. The DisplayDocTitle setting, which tells PDF viewers to show the title instead of the file name, was missing too. Without a language, a screen reader may read Italian text with an English voice, or the other way round. Without a title, people hear a file name such as “Document 3 final.pdf”.

Default and Off

For our small document, Accessibility “Default” gave the same result as “On”. Accessibility “Off” produced no tags at all.

What you can do

  • For documents that must be accessible, use another tool for the export. In our tests, Microsoft Word’s accessible export produced a well-structured tagged PDF (see our Word test, which also covers one problem to watch for). Adobe InDesign is another option for designed documents.
  • Or fix the PDF in a PDF editor that can rebuild the structure, such as a dedicated remediation tool.
  • If you stay with Pages, use its paragraph styles for titles, headings and lists, and keep Accessibility “On”. This does not solve the missing link between tags and content, but it gives a better starting point for remediation.
  • Set the language and the title afterwards. Pages has no setting for them; see how to set the language and title of a PDF on Mac.

How PDF Accessibility Checker helps

PDF Accessibility Checker shows you each of these problems in plain language: content not linked to tags, headings tagged as paragraphs, the generic H heading, the missing language and title.
