Invalid XMP metadata in PDFs from Word for Microsoft 365

Observed in 2026; article written in October 2026.

A single “&” in the author or company name can make a PDF lose its title in the eyes of strict validators. The cause is a small bug in how Word for Microsoft 365 writes metadata.

How we found it

We tested PDF Accessibility Checker against veraPDF on a set of public PDFs that had never been used to write the app’s rules (a “blind test”). One of them, a public document from an EU agency created with Word for Microsoft 365, was reported by veraPDF as having no title, although the title was clearly set. Reading the file directly showed the reason described below. We do not name the agency: the problem comes from the software, not from the authors.

What XMP metadata is

A PDF stores information about itself – title, author, subject, language, the PDF/UA identifier – in two places: the older Info dictionary and an XMP metadata packet. XMP is a small XML document embedded in the PDF. PDF/UA requires the title to be in the XMP metadata (dc:title).

What goes wrong

In XML, the character “&” has a special meaning and must be written as &amp;. When the author, the department or the company in the document properties contains “&” – for example “Research & Development” – Word writes it into the XMP (in dc:creator) without escaping it. The result is XML that is not well-formed.

A tolerant reader may skip over the error. A strict reader, such as veraPDF, cannot parse the packet and discards the whole metadata block. Everything in it is lost at once, including the title. The PDF is then reported as having no dc:title (veraPDF rule 7.1-9), and the PDF/UA identifier, if present, disappears too.

Assistive technology and PDF viewers vary in how they handle this. That is precisely the problem: the same file can look fine in one program and lose its title in another.

How to tell whether your PDF is affected

The symptoms are confusing, because the title looks fine in most places. The file name may be shown instead of the title in some viewers; a strict validator reports “no dc:title” or a missing PDF/UA identifier even though you set both; or one tool says the metadata is fine while another says it is missing. If you see any of these, look at the author, company and department properties of the source document: an “&” there is the most likely cause.

How to avoid it in Word

  • Before exporting, open File > Properties and look at the author, company and department fields (and any custom properties).
  • Replace “&” with “and” (or the equivalent in your language), then save the PDF again.
  • If your organization fills these fields automatically from a template or a directory, ask IT to avoid “&” in those values.

How to repair an existing PDF

If you cannot export the document again, the XMP packet has to be repaired: the special characters must be escaped so the XML becomes well-formed. PDF Accessibility Checker Pro does this automatically. It escapes the characters and keeps all the other properties as they were. If the packet is too damaged for that, it rebuilds a minimal valid packet with the essential information, such as the title. As always, the result is saved as a new file next to the original.

How PDF Accessibility Checker helps

The app checks whether the XMP metadata is well-formed – a check that many validators do not report as such – and tells you in plain language when it is not, instead of only saying that the title is missing.
