Word for Mac declares the wrong language in the PDF

Tested in October 2026 on macOS 27.

Microsoft Word for Mac can produce a very good accessible PDF. In our test it did almost everything right, except one detail that is easy to miss: it declared the wrong language.

How we tested

We wrote a fictitious sample document in Italian with headings, a bulleted list, a table with a header row, two images (one with alternative text, one without) and a link. Word’s interface was in English. We saved it as PDF in three ways and inspected each file with PDF Accessibility Checker, with veraPDF and by reading the PDF structure directly. These results describe this sample, this Word version and macOS 27; your results may differ.

The good news: an excellent tagged PDF

With File > Save As > PDF and the option “Best for electronic distribution and accessibility”, Word produced a well-structured tagged PDF:

  • a Document tag containing H1 and H2 headings;
  • a real list, with L, LI, Lbl and LBody tags;
  • a real table, with Table, THead, TBody, TR, TH and TD;
  • Figure tags for the images;
  • XMP metadata with the title (dc:title) and the DisplayDocTitle setting, so viewers show the title instead of the file name.

The remaining issues were small and expected: the image without alternative text (correctly reported, since we left it out on purpose), table header cells (TH) without a Scope attribute, and no PDF/UA identifier in the metadata.

Note that this option uses Microsoft’s online service to create the PDF, so the document is processed outside your Mac. Keep this in mind for confidential documents.

The problem: Lang = “en” for an Italian document

The PDF declared its language as English (Lang = “en”), although every word in it was Italian. The declared language matched the language of Word’s interface, not the language of the document.

Why does it matter? Screen readers use the declared language to choose the voice and the pronunciation rules. An Italian text read with English rules becomes hard or impossible to understand. Braille displays and translation tools rely on the language too. And because the PDF does declare a language, a basic check that only looks for “is there a language?” will report no problem.

The other export options are not accessible

  • “Best for printing” produced a PDF with no tags at all.
  • File > Print > Save as PDF (the macOS print panel) also produced an untagged PDF. In addition, it wrote the Mac user’s name into the Author field of the PDF, which you may not want in a published document.

How to fix it in Word

  1. Select all the text (Command-A) and choose Tools > Language. Pick the correct language for the document and confirm.
  2. If the document mixes languages, select each passage in another language and set its language the same way.
  3. Set the title in File > Properties.
  4. Save again with File > Save As > PDF and “Best for electronic distribution and accessibility”.
  5. Check the result.

How the app detects the mismatch

PDF Accessibility Checker compares the declared language with the language of the text. It takes a sample of pages, extracts the text and asks Apple’s NaturalLanguage framework which language it is. It reports a mismatch only when the detection has high confidence and there is enough text to judge: a document with a few words, or one that mixes languages evenly, is not flagged. When it does find a mismatch, it shows a warning such as “The declared language is not the language of the text”.

How PDF Accessibility Checker helps

The app finds the wrong language that other checks miss, and explains how to correct it in Word. With Pro, it can also set the language for you: it proposes the language detected from the text, writes it into a new file named name-accessible.pdf next to the original, and checks the new file again. It can also remove the author and document metadata, such as the author name added by the print panel. Learn more about PDF Accessibility Checker.
